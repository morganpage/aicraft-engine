## Phase 5 — NineSlice + FullSize\* (the third LDtk gap)

Research results that shape this (**[review] all re-verified**): exactly six in-repo NineSlice defs across three fixtures, every one carrying non-empty uniform `[n,n,n,n]` borders — `Entities.ldtk` Door `[6,6,6,6]` (12×32) and TriggerArea `[5,5,5,5]` (16×16); `Typical_2D_platformer_example.ldtk` Door `[5,5,5,5]` (12×32); `Typical_TopDown_example.ldtk` Door `[4,4,4,4]` (16×16), Button `[4,4,4,4]` (10×10), SecretWall `[4,4,4,4]` (16×16). The schema fixes the border order **up/right/down/left** and defers scaling semantics to the 9-slice Wikipedia article; **no fixture anywhere uses FullSize\*** (confirmed — zero occurrences). One degenerate case ships in-repo: `Entities.ldtk`'s Door (borders at **`:1484`**, not `:1481-84`) is 12px wide against 6+6 borders — a **zero-width center** at default size. The other two narrow defs are merely tight, not degenerate (2px centers).

1. **Parse** (`src/ldtk/parse.ts` `parseEntityDef`, `src/ldtk/types.ts` `LdtkEntityDef`): `readonly nineSliceBorders: readonly [number, number, number, number] | null` — a 4-finite-int array parses to the tuple **in up/right/down/left order**, anything else (absent, empty, wrong arity) → `null`. Barrel-export nothing new beyond the type if it needs naming.
2. **Render** (`src/ldtk/render.ts`): `drawLdtkEntityTile` gains an optional trailing `nineSliceBorders` param. `NineSlice` with borders → standard 9-slice (corners 1:1, top/bottom edges stretch horizontally, left/right stretch vertically, center both); **under-sized dest clamps each border to `min(border, floor(dim / 2))`**, documented in the JSDoc as deliberate since the schema is silent.

   **[review] The clamp alone does not solve the Door.** `min(6, floor(12 / 2)) = 6`, so left + right = 12 = the full dest width and the center strip comes out **exactly zero-wide** — the clamp prevents a *negative* span, not a zero one, and the plan's own headline edge case still lands on a broken draw. A zero source or dest dimension in `drawImage` is an error condition, not a silent no-op. **Add an explicit rule: skip any slice whose computed source or dest width/height is ≤ 0.** **[review²] the surviving slices, corrected:** with uniform borders the ≤ 0 rule drops the center strip AND the top/bottom edge strips (their dest width is zero), but the left/right edge strips still draw — dest 6 wide × 20 tall, stretched from the source's 6×4 side strips — alongside the four 1:1 corners; corners alone (6×6 each) cannot tile a 12×32 rect. That is the correct degenerate rendering: the door's sides stretch down its full height and only the horizontal center collapses. Test both: the clamp case (odd dest, borders exceeding half) and the zero case (the Door at 12 wide, `[6,6,6,6]`), asserting no zero-size draw is ever issued. `NineSlice` with `null` borders → the existing geometry fallback (unchanged contract for files that lost the field). `FullSizeCropped` / `FullSizeUncropped` → native-size blip, clipped / unclipped to the rect (schema names but does not define them; JSDoc says so) — ~10 lines, closes the enum.
