# In-App Purchase (IAP) Bridge Abstractions

> Research note for in-app purchase (IAP) bridge abstractions. Slug: `iap-bridge`.
> Investigated: 2026-06-20.

## TL;DR

An in-app purchase (IAP) bridge abstracts platform-specific commerce APIs (Apple StoreKit 2, Google Play Billing, Poki SDK, Jest SDK, Steam Microtransactions) behind a single, unified, and defensive TypeScript interface suitable for a zero-dependency game engine. This note surveys unified billing patterns, client-side entitlement caching, receipt validation trade-offs, and platform-specific behaviors. For `aicraft-engine`—which must maintain strict determinism in its simulation core—we propose three key architectural pillars: (1) a **Deterministic Asynchronous Event Queue** to bridge non-deterministic, host-touching transaction callbacks safely into the game's tick loop, (2) an **Ad-to-Unlock Proxy Adapter** for ad-monetized platforms like Poki, allowing the same game code to run unmodified across ads-only and IAP-only channels, and (3) a **LocalStorage-Backed Mock Billing Adapter** for seamless, zero-overhead offline development and automated testing.

## Why this matters for aicraft-engine

- **Pillars Touched**: Directly establishes **Pillar 3 (IAP Bridge)**, integrates with **Pillar 2 (Cosmetics / Palette)**, and prepares **Pillar 5 (Platform Adapters)**.
- **Consumer Games**: Sibling games like *Spitekeep* and future Clone-to-Jest titles require a robust monetization surface. Since Jest is strictly IAP-only (no ads allowed), converting proven ad-monetized loops into IAP-driven loops is the primary commercial engine of the pipeline.
- **Unlocks**:
  - **Premium Cosmetics Surface**: Allows players to buy procedural skin presets, particle effects, and custom animations generated by Pillar 2.
  - **One-Time Content Unlocks**: Enables permanent unlocks of advanced chapters, worlds, or game modes.
  - **Dual-Publishing Flexibility**: Allows a single codebase to be compiled for Poki (ads-only monetization via rewarded ad proxies) and Jest (direct IAP monetization).
  - **Zero-Dependency Portability**: Ensures the game can be wrapped in WebViews for iOS/Android, shipped to web platforms like Jest/Poki, or compiled for desktop (Steam/itch.io) without dragging in heavy, platform-specific SDKs or breaking the zero-runtime-dependency rule.

## Prior Art Survey

### Pattern 1: Event-Driven Unified Store Interface
- **Source**: Unity IAP (`IStoreListener` / `IStoreController`) & `cordova-plugin-purchase` (Fovea)
- **What it does**: Unifies disparate store frontends (App Store, Google Play, Web) behind a single reactive controller and transaction listener. It separates store initialization, product catalog querying, purchase requests, and transaction state updates into a clean, asynchronous lifecycle.
- **Algorithmic shape**:
  ```typescript
  export type ProductType = 'non_consumable' | 'consumable' | 'subscription';

  export interface IAPProduct {
    readonly id: string;
    readonly type: ProductType;
    readonly title: string;
    readonly description: string;
    readonly price: string;       // Formatted price string (e.g., "$1.99")
    readonly priceMicros: number; // Raw price in micro-units (e.g., 1990000)
    readonly currencyCode: string; // ISO 4217 code (e.g., "USD")
  }

  export interface IAPTransaction {
    readonly id: string;
    readonly sku: string;
    readonly state: 'pending' | 'approved' | 'finished' | 'failed';
    readonly receipt?: string;
    readonly error?: string;
  }

  export interface IAPBridge {
    initialize(): Promise<void>;
    isInitialized(): boolean;
    getCatalog(): readonly IAPProduct[];
    purchase(sku: string): Promise<IAPTransaction>;
    restore(): Promise<readonly IAPTransaction[]>;
    onTransaction(callback: (tx: IAPTransaction) => void): () => void; // Returns unsubscribe function
  }
  ```
- **Determinism profile**: Host-touching and highly asynchronous. Store initialization, network latency, and user payment interactions are inherently non-deterministic.
- **Runtime cost**: Negligible. Network requests are amortized at startup or triggered on explicit user actions (clicking "buy" or "restore").
- **Dependencies**: None. The interface is pure TypeScript, and platform-specific implementations resolve their host SDKs lazily at runtime.
- **Fit for our constraints**: Strong. It provides a clean boundary between host-specific billing logic and the game's simulation core.
- **What to steal**: **Reactive transaction callbacks**. Instead of relying solely on a purchase promise (which can easily be lost if the app crashes, the page reloads, or the network drops mid-transaction), the bridge must support a persistent transaction listener (`onTransaction`) that fires whenever a transaction state updates. This matches App Store and Google Play guidelines for handling interrupted purchases.
- **What to avoid**: Avoid blocking the main thread or making synchronous calls to host APIs. All billing calls must be asynchronous.

### Pattern 2: Ad-to-Unlock Proxy Adapter
- **Source**: Poki SDK (`rewardedBreak`) & CrazyGames SDK
- **What it does**: Maps IAP purchase requests directly to rewarded ad completions on ad-monetized web platforms. This allows a game to use a single, unified "unlock" code path. On Jest, the player pays $0.99; on Poki, the player watches a 15-second rewarded ad. The adapter translates `purchase(sku)` into a rewarded ad break, reporting a successful "transaction" if the ad completes.
- **Algorithmic shape**:
  ```typescript
  export function createPokiIAPAdapter(pokiSdk: any): IAPBridge {
    let initialized = false;
    const listeners = new Set<(tx: IAPTransaction) => void>();

    return {
      async initialize() {
        initialized = true;
      },
      isInitialized() {
        return initialized;
      },
      getCatalog() {
        // Map premium SKUs to virtual "Ad-Unlock" products with zero price
        return [
          { id: 'skin:neon_devil', type: 'non_consumable', title: 'Neon Devil Skin', description: 'Unlock via Ad', price: 'Free (Ad)', priceMicros: 0, currencyCode: 'USD' }
        ];
      },
      async purchase(sku: string): Promise<IAPTransaction> {
        const txId = `poki-ad-${Date.now()}-${Math.floor(Math.random() * 1000)}`;
        
        // Trigger rewarded ad break as a proxy for purchase
        return new Promise((resolve) => {
          pokiSdk.rewardedBreak()
            .then((success: boolean) => {
              if (success) {
                const tx: IAPTransaction = { id: txId, sku, state: 'approved' };
                listeners.forEach(cb => cb(tx));
                resolve(tx);
              } else {
                const tx: IAPTransaction = { id: txId, sku, state: 'failed', error: 'Ad skipped' };
                listeners.forEach(cb => cb(tx));
                resolve(tx);
              }
            })
            .catch((err: any) => {
              const tx: IAPTransaction = { id: txId, sku, state: 'failed', error: String(err) };
              listeners.forEach(cb => cb(tx));
              resolve(tx);
            });
        });
      },
      async restore() {
        // Poki doesn't persist ad unlocks across sessions natively unless cached in player save
        return [];
      },
      onTransaction(callback) {
        listeners.add(callback);
        return () => listeners.delete(callback);
      }
    };
  }
  ```
- **Determinism profile**: Host-touching and non-deterministic (depends on ad network fill rates and user behavior).
- **Runtime cost**: Low. Only runs on explicit user click.
- **Dependencies**: None. The Poki SDK is passed in or resolved lazily from `window.PokiSDK`.
- **Fit for our constraints**: Strong. It is the key to the **Clone-to-Jest dual-publishing strategy**, allowing a single codebase to support ads on Poki and IAP on Jest.
- **What to steal**: **Virtual product mapping**. Mapping real-money SKUs to ad-unlocked items dynamically based on the active adapter.
- **What to avoid**: Do not trigger ad breaks automatically or without explicit user consent. Poki strictly bans unprompted ads.

### Pattern 3: Client-Side Cryptographic Receipt Validation
- **Source**: Apple StoreKit 2 (JWS Transactions) & Google Play Billing (RSA Signatures)
- **What it does**: Validates platform-signed purchase receipts directly on the client device without requiring a game server. For Apple, this involves parsing the JSON Web Signature (JWS) transaction token and verifying it against Apple's Root Certificate. For Google, it involves verifying the SHA256withRSA signature of the purchase JSON using the developer's Base64-encoded public key.
- **Algorithmic shape**:

- **Determinism profile**: Pure mathematical operations (fully deterministic once keys and signatures are provided).
- **Runtime cost**: Medium. Cryptographic signature verification (RSA/ECDSA) takes a few milliseconds of CPU time, but is only executed once per purchase or restore.
- **Dependencies**: Heavy dependency risk. Standard JS cryptographic libraries (like `node-forge` or `elliptic`) are large and violate our zero-runtime-dependency constraint. While the modern **Web Crypto API** (`window.crypto.subtle`) is built into all target browsers and WebViews, it is completely asynchronous (Promise-based) and unavailable in Node.js test environments without polyfills.
- **Security Trade-off**:
  - **Client-side validation is highly vulnerable to spoofing**. On web platforms, players can easily inspect the page, inject JS, or modify their `localStorage` save file to grant themselves any skin. On wrapped iOS/Android apps, tools like *LocalAPStore* or *Lucky Patcher* easily intercept WebView bridges to return fake success receipts.
  - **However, for cosmetics-only casual games, this risk is acceptable**. A procedural skin preset (e.g., a neon outline) has no gameplay impact and does not affect competitive balance. If a dedicated player hacks their local save to unlock a skin, it does not hurt other players or cost the developer server bandwidth.
  - **Recommendation**: For v1, the library should **delegate cryptographic validation to the host wrapper** (e.g., the Capacitor/Cordova native layer or the Jest platform itself) and trust the local adapter's resolved promise. The library's job is to act as a bridge and cache entitlements defensively in the player's save file, not to run a heavy cryptographic suite.
- **What to steal**: **Defensive receipt caching**. Storing the raw transaction ID or receipt string in the local save file alongside the unlocked skin ID. If the local save is ever synced to a backup cloud, the receipts can be re-validated later.
- **What to avoid**: Avoid bundling heavy cryptographic libraries into `aicraft-engine`. Do not write custom, fragile JS-based RSA parsers.

### Pattern 4: Local Mock Storage & Dev Adapters
- **Source**: Sibling Spitekeep `SaveStorage` & local development practices
- **What it does**: Implements mock billing adapters that simulate real platform transaction flows. The memory adapter stores purchases in an in-memory array (perfect for automated unit tests), while the localStorage adapter persists mock purchases in `localStorage` (perfect for local development and testing the purchase/restore flow without spending real money).
- **Algorithmic shape**:
  ```typescript
  export function createLocalStorageIAPAdapter(storageKey = 'mock-iap-entitlements'): IAPBridge {
    let initialized = false;
    const listeners = new Set<(tx: IAPTransaction) => void>();

    const getSavedSkus = (): string[] => {
      try {
        const raw = window.localStorage.getItem(storageKey);
        return raw ? JSON.parse(raw) : [];
      } catch {
        return [];
      }
    };

    const saveSku = (sku: string) => {
      try {
        const skus = getSavedSkus();
        if (!skus.includes(sku)) {
          skus.push(sku);
          window.localStorage.setItem(storageKey, JSON.stringify(skus));
        }
      } catch {}
    };

    return {
      async initialize() {
        initialized = true;
      },
      isInitialized() {
        return initialized;
      },
      getCatalog() {
        return [
          { id: 'skin:neon_devil', type: 'non_consumable', title: 'Neon Devil', description: 'Seeded Neon Skin', price: '$0.99', priceMicros: 990000, currencyCode: 'USD' },
          { id: 'chapter:world_2', type: 'non_consumable', title: 'World 2 Unlock', description: 'Unlock World 2 Levels', price: '$2.99', priceMicros: 2990000, currencyCode: 'USD' }
        ];
      },
      async purchase(sku: string): Promise<IAPTransaction> {
        const txId = `mock-tx-${Date.now()}`;
        return new Promise((resolve) => {
          // Simulate short network delay
          setTimeout(() => {
            saveSku(sku);
            const tx: IAPTransaction = { id: txId, sku, state: 'approved' };
            listeners.forEach(cb => cb(tx));
            resolve(tx);
          }, 500);
        });
      },
      async restore(): Promise<readonly IAPTransaction[]> {
        const skus = getSavedSkus();
        return skus.map((sku, idx) => ({
          id: `mock-restore-${idx}`,
          sku,
          state: 'approved'
        }));
      },
      onTransaction(callback) {
        listeners.add(callback);
        return () => listeners.delete(callback);
      }
    };
  }
  ```
- **Determinism profile**: Host-touching (localStorage) or pure (memory). Mock timers can introduce non-determinism if called mid-simulation, but are safe when isolated.
- **Runtime cost**: Negligible.
- **Dependencies**: None.
- **Fit for our constraints**: Strong. Essential for testing and local development.
- **What to steal**: **Simulated network delay**. Using `setTimeout` in the mock adapter to simulate real-world asynchronous latency, helping developers catch race conditions in their UI code (such as a player clicking a "buy" button multiple times before the transaction resolves).
- **What to avoid**: Avoid persisting mock purchases in production builds. The adapter factory must select the real platform adapter when running in production.

### Pattern 5: Pure Entitlement Progression Ops
- **Source**: Sibling Spitekeep `progress.ts` & `src/cosmetics/ownership.ts`
- **What it does**: Implements pure, immutable state transitions for managing entitlements. It takes the current save state, maps the purchased SKU to its corresponding game asset (such as a skin ID or chapter unlock) using a mapping configuration, and returns a fresh, deep-cloned save state with the entitlement granted.
- **Algorithmic shape**:
  ```typescript
  export interface EntitlementSave extends CosmeticSave {
    /** Array of active purchased SKUs, sorted and deduped. */
    entitlements: string[];
  }

  export type SkuResolver = (sku: string) => { type: 'skin' | 'chapter'; targetId: string } | null;

  /**
   * Pure progression op: grant an entitlement based on a purchased SKU.
   * Immutable in -> JSON-clone out -> never throws.
   */
  export function grantEntitlement(
    save: EntitlementSave,
    sku: string,
    resolver: SkuResolver
  ): EntitlementSave {
    if (typeof sku !== 'string' || sku.length === 0) {
      return JSON.parse(JSON.stringify(save)) as EntitlementSave;
    }

    // 1. Deep clone the save defensively
    const next = JSON.parse(JSON.stringify(save)) as EntitlementSave;
    if (!Array.isArray(next.entitlements)) next.entitlements = [];
    if (!Array.isArray(next.owned)) next.owned = [];

    // 2. Add SKU to entitlements array (sorted and deduped)
    if (!next.entitlements.includes(sku)) {
      next.entitlements.push(sku);
      next.entitlements.sort();
    }

    // 3. Resolve the SKU to grant the actual game asset
    const resolution = resolver(sku);
    if (resolution) {
      if (resolution.type === 'skin') {
        // Compose with grantSkin logic
        if (!next.owned.includes(resolution.targetId)) {
          next.owned.push(resolution.targetId);
          next.owned.sort();
        }
      } else if (resolution.type === 'chapter') {
        // Handle chapter unlocks (e.g., adding to an unlockedChapters list)
        // For v1, this can be represented by storing the chapter ID in a dedicated array
      }
    }

    return next;
  }
  ```
- **Determinism profile**: Pure mathematical and object operations. Fully deterministic.
- **Runtime cost**: Negligible. Only called on transaction success events, never per-frame.
- **Dependencies**: None.
- **Fit for our constraints**: Strong. It matches the pure progression patterns established in Spitekeep and `src/cosmetics/ownership.ts`.
- **What to steal**: **Decoupled SKU resolution**. Keeping the mapping between store SKUs (e.g., `'com.company.game.neon_devil'`) and game-internal IDs (e.g., `'devil-neon'`) outside the core save structure. This allows the developer to change store SKUs on Apple/Google without having to migrate the player's local save file.
- **What to avoid**: Never mutate the input save object. Never throw errors on unrecognized SKUs; degrade to a silent no-op (returning a valid cloned save).

## Open Questions

- **Consumable Purchases (v2 Scope)**:
  Cosmetics are non-consumable (buy once, own forever), which is easy to model and restore. If we support consumables (e.g., skip tokens, revive hearts) in v2, how do we prevent local save-editing exploits in a client-only library?
  *Draft Answer*: We must acknowledge that in a serverless, client-only web game, local save-editing is trivial. To mitigate this without a server, we can encrypt the save file using a simple obfuscation key (e.g., XOR with a game-specific salt) to deter casual players, but we must accept that determined hackers can always bypass client-side security.
- **Refunds and Revocations**:
  If a player requests a refund through Apple/Google, the platform revokes the entitlement. How does the client-side bridge detect this?
  *Draft Answer*: When the app starts and the bridge initializes, it queries the active entitlements via `restore()` or `getEntitlements()`. If a previously-owned SKU is missing from the platform's active list, the bridge can trigger a `revokeEntitlement(save, sku)` pure op to remove the skin from the player's save file.
- **StoreKit 2 JWS Parsing**:
  StoreKit 2 returns transactions encoded as JWS (JSON Web Signature) strings. Parsing and verifying JWS requires a cryptographic library. Should `aicraft-engine` include a lightweight base64-decoder to extract the payload without verifying the signature, or should we rely entirely on the native iOS wrapper to decode the transaction before passing it to JS?
  *Draft Answer*: The native iOS wrapper (e.g., Capacitor plugin) should handle the JWS decoding and pass a clean, parsed JSON object to the JS bridge. This keeps `aicraft-engine` completely zero-dependency and lightweight.

## Top 3 Patterns Worth Prototyping

1. **Deterministic Asynchronous Event Queue** — Prototyping a simple, zero-dependency event queue that collects asynchronous transaction callbacks and flushes them deterministically on the next game tick, preventing non-deterministic simulation state mutations.
2. **Dual-Publish Ad-to-Unlock Proxy (Poki Adapter)** — Prototyping an adapter that maps `purchase(sku)` to `PokiSDK.rewardedBreak()`, proving that the same game-level purchase UI can drive ad-monetization on Poki and direct IAP on Jest.
3. **LocalStorage-Backed Mock Billing Adapter** — Prototyping a localStorage-backed mock store that simulates network latency, purchase approvals, and purchase restorations, enabling complete offline testing without platform sandboxes.
