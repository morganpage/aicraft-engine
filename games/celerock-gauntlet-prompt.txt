I want you to build a Celeste-class precision platformer that plays the supplied LDtk level, following the directions in the file:

https://github.com/morganpage/aicraft-engine/blob/v0.22.10/games/celerock.md

Done is defined by the brief's §12.7 acceptance criteria, §12.8 forbidden patterns, §12.9 required wiring, and §12.10 gate substance — not by a critic's enthusiasm. The sequencing is fixed and non-negotiable: **wire the engine first, get it correct and complete, then one bounded polish pass.** Two runs of this prompt have proven what happens otherwise. One shipped 5,300 lines of TypeScript across twenty files with all fourteen recipes copied and twelve wired, twelve test files, a Playwright pixel-probe harness, and every §13 gate captured. The other shipped **420 lines in a single `src/main.js` whose only import was `./style.css`** — `aicraft-engine` in `package.json` at `^0.17.2`, never imported once, gravity hand-integrated, tiles hand-blitted from `gridTiles`/`autoLayerTiles`, `Player.json` never compiled. Its platforms did not autotile, its animations were wrong, and it looked like a platformer in a screenshot. **A screenshot critic cannot tell those two builds apart. That is why the critic is not the gate.**

## Start from the scaffold — do not scaffold it yourself

Copy `games/celerock-starter/` out of the engine repo and build there. It ships **§14 Stage 1 complete and working** (boot, the G3 preflight, the painter over the surface cache, the Celeste camera preset, the letterbox, the DPR boundary, and the one `composeCameraTransform` render skeleton every later stage inherits), the twelve §1.1 recipes already in `src/recipes/`, the assets in `public/`, the exact pin, and the gates wired to `pretest`/`prebuild`.

This exists because the previous run had this prompt in full, fetched it, and copied no recipes, wrote no tests, captured no gates — while producing a BUGFIXES.md about backdrop star scatter. Not defiance: cost. Fetching and copying twelve files shows no progress on screen, so a run under pressure skips it and re-sketches inline. In the scaffold the recipes are already there, so importing costs one line and re-sketching costs forty — the cheap path and the correct path are finally the same path.

Your job is Stages 2–7. Bump `config.stage` in `package.json` as each lands; `bash gate/check.sh --stage N` then gates exactly that stage, and the next one goes red until you build it. **Do not modify anything under `gate/`.** Deleting the `pretest`/`prebuild` hooks or shortening `gate/gates.ts` are the one-line ways to defeat this, both fail `tests/contracts.test.ts`, and both show up in `git diff gate/`.

## Build order and gates

- If your harness has sub-agents, fan out one per brief §14 stage (Stages 1–7). If it does not, work the stages sequentially in one thread — nothing below depends on parallelism, only on the stages being worked in order and each one's gate passing before the next begins.
- A stage is DONE when its mechanical checks pass: the §12.9.1 recipe greps, the §12.9.2 engine-reachability greps, the §12.9.3 wiring loop, the §12.8 forbidden-pattern scan, `npx tsc --noEmit` clean, the stage's §14 gate, and a headless screenshot showing the stage's feature actually working. Nothing else gates a stage — not a critic, not a vibe, not a subagent's own summary of its work.
- **Run the gate at EVERY stage boundary, not once at the end.** It is already in the scaffold at `gate/check.sh` and already on `pretest`/`prebuild`; run `bash gate/check.sh --stage N` as each stage closes. It prints nothing and exits 0 when clean. `grep -rn --exclude-dir=recipes "from 'aicraft-engine'" src/` must hit game code; `createLdtkRoomPainter`, `stepPlatformer`, `drawSprite` and `deriveSpriteAnimKind` must each appear outside `src/recipes/`. The `--exclude-dir=recipes` is the entire point: the copied recipes import the engine themselves, so a grep over all of `src/` comes back green for a build that carries fourteen recipes and wires none of them. The failed run would have been caught by these greps at Stage 1 and was instead discovered by a human playing it.
- **TypeScript, exact pin, multi-file.** `"aicraft-engine": "0.22.0"` with no caret (a caret range resolved the failed build to `0.17.2`, five minors below the API the brief describes). No `.js` in `src/` — a `src/main.js` silently voids `tsc --noEmit` as a gate, which is how 420 unchecked lines ship against an API nobody read. If the whole game is one file, the recipes are not in it and neither is the engine.
- **§12.9 is necessary, not sufficient — §12.10 is the other half.** A later run of this prompt passed all forty-one §12.9 checks (TypeScript, exact pin, twelve recipes wired, `tsc` clean, suite green) and still shipped a fifth of a game with an empty `.qa/`, because its §13 gate assertion was `missingShotManifest(dir, [])` — the exact function the brief names, called correctly, requiring nothing. Given a mechanical gate, a run under pressure finds its weakest legal reading. At Stage 7 run `./celerock-wiring-check.sh --final`: fifteen captures minimum, twenty-five tests minimum, and the five §12.10.2 subjects actually tested. It cannot pass earlier, so do not run it earlier.
- Stages 1–4 may look plain. Do not spend rounds on art direction before the full §12.7 checklist passes — a correct game with an untinted tileset beats a pretty one that hand-rolls the kernel.

## Critic protocol (after §12.7 passes, not before)

- Polish is ONE final pass after §12.7, §12.8 and §12.9 all pass: at most 2 critic rounds, then ship regardless. "Wowed" is not a terminal condition a critic can define, and an uncapped harsh-critic loop does not converge — it converges on whatever is cheapest to restyle, which is never the kernel.
- Each polish round has one deliverable: the critic compares the CURRENT screenshot against the PREVIOUS round's screenshot, names the single biggest remaining defect, and the builder fixes that one thing. If the fix makes the screenshot worse, revert it. Never compare a mid-build screenshot against Celeste marketing shots — that is a finished commercial game with artist art, an unwinnable bar that fuels endless elaboration.
- Before critiquing anything, the critic reads §12.7 and §13 and is bound by them. The 15 gates in §13 are the critique surface; anything outside them, and anything on the §15 stretch list, is OUT OF SCOPE — log the suggestion in the critique file and move on.
- **The critic is bound by a standing list of intentional differences and may not raise any of them:** the tileset is CC0 teal cave art ("Tranquil Tunnels"), not Celeste's mountain. The player is the CC0 "Deep Night" sheet, not Madeline. The letterbox bars around the 320×184 window are Celeste's fixed lens, working as specified (§12.7 #20). One dash, not two. The shipped level is what the `.ldtk` contains — the `.ldtk` is never edited to add content a critic wants to see.
- The critic writes its critique file to `.qa/` BEFORE replying, so the critique survives a lost reply. (Sub-agent harnesses only: an empty reply means "resume it", not "rerun it".)
- After the polish pass, run ONE blind side-by-side against real Celeste gameplay screenshots — informational only, feeding the postmortem; it never reopens the build. Curate like-for-like references first (gameplay frames at similar zoom, not cutscenes or key art) and perturb one pixel of each panel before uploading so content-hash dedup cannot break the blinding.

## Complexity budget — a floor as well as a ceiling

The failed run failed by being too small, so the floor is the load-bearing half:

- **Floor:** `src/` is multi-file per §11's layout. `src/recipes/` holds the §1.1 copy-ins verbatim. `tests/` holds every artifact §12 names, and they test GAME code — a suite that only drives engine functions is the suite a real build shipped green while every wiring defect it had went undetected (§12 preamble).
- **Ceiling:** `index.html` ≤ 60 lines. No npm dependencies beyond `aicraft-engine` and dev tooling (typescript/vite/vitest; playwright/pngjs as devDependencies for the harness is fine, never shipped in the page). No web fonts, no `@fontsource`, no CDN assets — the bitmap font is the only text path (`fillText` is a §12.8 forbidden pattern). No DOM chrome: no HUD divs, no `backdrop-filter` glass panels, no vignette overlays. The game is the canvas.
- If a file exceeds its budget you are building chrome the brief does not ask for — delete the chrome, do not restructure the file. If a file is far under, check §12.9 before congratulating yourself on the line count.

## Operational notes, learned from previous runs of this exact prompt

- Verify visually with pixel probes (count pixels of an expected colour in a region), not by asking a vision model to describe the screenshot — models misread framing and hallucinate features. The brief's §13 gates name what each shot must prove; assert the shot manifest (`missingShotManifest` from `recipes/game-test-harness.ts` returns `[]`) so a gate whose capture silently skipped fails the suite instead of shipping as a dangling reference.
- Validate the brief's example probes against one real render at Stage 1 and freeze the passing values into a conventions doc. A probe that has never passed is worse than no probe.
- Before declaring any stage done, confirm the recipe files were actually COPIED into `src/recipes/` and imported — not re-sketched inline. A stage that reimplements a recipe from scratch is a failed stage, however good the code looks. The import grep must match both depth forms (`./recipes/` and `../recipes/`): game code lives in `src/` and `src/game/`, and the obvious one-form grep silently misses half the call sites.
- After any interrupted or cancelled unit of work, check the working tree before redoing it (`git status` + `npx tsc --noEmit` + a smoke screenshot): interrupted work has usually already written complete code to disk, and redoing it wastes the whole round.
- Before starting, kill any Vite dev server left running by a previous gauntlet run (check the port): a stale server returns 200 and you will test the wrong game.
- Do not drive stage iteration with a scheduler, timer, or recurring-run feature of your harness (Claude Code's `/loop` is one example). Those are interval runners, not iteration primitives. The iteration structure you want is the §14 stage list with its gates: finish a stage, run `bash gate/check.sh --stage N`, move on.
- The §12.8 scan runs as a test (`scanForbiddenIdentifiers('src') === []`), not as a manual grep nobody runs. Same for §12.9 — put both loops in the suite the moment Stage 1 has a suite.
- **If your harness drives an interactive browser tab (not headless Playwright) for manual verification, its synthetic key-press action may not set `KeyboardEvent.code`/`keyCode` at all — only `.key`.** This brief's own keyboard map is `.code`-based (Celeste's physical-key layout, §4.3), so a tool whose synthetic presses omit `.code` will silently fail to drive the game and look like a dead build. Confirm which fields your tool's key action actually sets before concluding input is broken; the fix, if it is missing, is to dispatch a real `KeyboardEvent` yourself (`window.dispatchEvent(new KeyboardEvent('keydown', { code: 'KeyC', bubbles: true }))`) rather than assume the game is unresponsive. The same tab's `requestAnimationFrame` may also only fire in bursts triggered by a screenshot/paint request rather than on a steady clock — expect a held key to sometimes complete its whole action (a full jump arc, a whole dash) between one screenshot and the next, and don't mistake that for the input never landing.
- **Scripted input gotchas, both earned by the 2026-08-27 run.** Variable jump height follows HOLD TIME — a 60 ms key tap is a minimum-height hop that cannot clear a full-tile step, and a scripted bot pinned against Level_0's first step for two full minutes before anyone looked at hold duration; hold scripted jumps ~220 ms. And when placing a player for a capture, edit ONLY position/velocity through the exposed game object — replacing session state with a plain object kills the fixed-step loop within three ticks (`pollRoomTransition` throws on the malformed detector; the loop stops by design), while placement-only edits are safe because the detector's containment latch re-derives from geometry on every poll.

## Ship condition

The run ends when: every §14 stage is built, the full §12.7 checklist passes, §12.8, §12.9 and §12.10 come back clean, the §13 gates are captured as FILES the manifest names, and the polish pass (≤ 2 rounds) is complete.

Then write a postmortem to `games/postmortems/celerock-<YYYY-MM-DD>.md` in the engine repo — what the greps caught and when, which stage gates failed on the first attempt, the final §12.9 output, the blind-comparison result, and every out-of-scope suggestion the critic logged. **This file is the only mechanism by which the next revision of this prompt gets smarter.** The failed run taught nothing for a year because nobody wrote one; every hardened paragraph above exists because a specific run failed in a specific, describable way. Then stop.
